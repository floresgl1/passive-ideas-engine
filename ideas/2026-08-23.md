## Step 3 — Ideas

### 1. Failure-Taxonomy Retry Library — [Leverage]
- competence: unlabeled
- labeled_at: —

**Idea:** Package stripe-reconciler's three distinguished OAuth failure categories
(NeedsReauthorization / transient token-endpoint error / manifest permission gap) alongside
finance_bot's enumerated trading-error categories into one importable library that classifies a raw
exception from any third-party API into a named category with its own default retry policy, instead
of every integration re-inventing its own ad hoc error handling.
**Leverages:** LLM agent engineering `[strong]` (finance_bot's enumerated error categories, bounded
retry budgets) and this week's stripe-reconciler OAuth work, where three previously-conflated
failures were split apart at one chokepoint (`stripe_auth()`).
**One new thing to learn:** Generalizing two domain-specific taxonomies (a payments API and a
trading API) into one shared classification interface that still lets each caller register its own
categories, rather than hardcoding either domain's specifics into the shared core.
**Why it's worth it:** Both taxonomies already exist, are tested, and run in production; the
remaining work is bounded integration into one shared library, with a clear buyer in anyone
integrating a third-party API who currently treats every failure as the same generic exception.
**First step today:** Pull finance_bot's enumerated error categories and stripe-reconciler's three
OAuth failure types into one shared table, and write the single dispatch function that maps a raw
exception from either domain to `(category, default_retry_policy)`.

### 2. Currency Minor-Unit Formatting Guard — [Passive]
- competence: unlabeled
- labeled_at: —

**Idea:** Extract ledger-core's per-currency minor-unit exponent table into a standalone,
zero-dependency guard library (and a matching small hosted validation endpoint) that others can drop
into any money-handling codebase to catch the exact bug class it was built to fix — a flat
two-decimal formatter silently rendering 150 JPY as "1.50 JPY."
**Leverages:** Relational / double-entry data modeling `[strong]`, specifically ledger-core's
already-built, already-tested per-currency exponent table and its dedicated money-formatting test
suite.
**One new thing to learn:** Packaging the table as a standalone, framework-agnostic checker (a
pre-commit hook, a CI lint step, or a small validation endpoint) that scans formatted-money output
for exponent mismatches, rather than only using it internally inside ledger-core's own formatter.
**Why it's worth it:** The correctness logic and its test suite are already written and proven; what
remains is exposing it as an installable guard against a narrow, concrete, and genuinely
embarrassing bug class — a strong, self-explaining pitch for a small sold package.
**First step today:** Pull the exponent table out of ledger-core's formatter module, wrap it in a
single `check_amount(amount, currency, formatted_string)` function with no other ledger-core
imports, and test it against the exact original JPY case.

### 3. Alpaca Order-Compatibility Preflight Checker — [Experience]
- competence: unlabeled
- labeled_at: —

**Idea:** Generalize the still-open, load-bearing Direction & Intent step — "verify fractional-share
+ OTO stop-loss compatibility in Alpaca paper before any live deployment" — from a one-off check
into a reusable preflight tool that submits a matrix of order-type combinations (fractional vs.
whole share, OTO/OCO/bracket, stop-loss variants) against Alpaca's paper API and reports which
combinations are accepted, silently rejected, or silently reinterpreted.
**Leverages:** Production observability and failure handling `[strong]` plus finance_bot's existing,
already-running Alpaca execution integration `[emerging]`.
**One new thing to learn:** Systematically enumerating and testing Alpaca's order-type combination
space, rather than only exercising the single combination finance_bot currently uses — the gap
between "our one order type works" and "here's what does and doesn't across the space."
**Why it's worth it:** It closes a named, currently-blocking gap for finance_bot's own next
deployment step, and the resulting compatibility matrix is also a repeatable, sellable check for
other hobbyist Alpaca algo-traders facing the identical live-deployment question.
**First step today:** Write the order-combination matrix as a plain list (share type × order type ×
stop-loss variant) and submit the first three combinations against Alpaca's paper endpoint, logging
accepted vs. rejected vs. silently-modified for each.

### 4. Kernel-Space Character Device Driver Kit — [Stretch]
- competence: unlabeled
- labeled_at: —

**Idea:** Build a minimal Linux character-device kernel module (load, read/write, unload) with a
simple ioctl-driven interface, documenting each kernel-vs-user-space boundary crossing as it's
built, then package the finished module plus its documentation as a downloadable reference kit for
the "Linux kernel basics" line named in Direction & Intent.
**Leverages:** Systems programming `[emerging]` (CSE4600-HW1's process lifecycle, IPC, and
concurrency primitives) as the nearest shipped base, plus hardware–software boundary reasoning
`[conceptual]` as the driver-placement lens.
**One new thing to learn:** Kernel module development itself — module init/exit, character device
registration, `copy_to_user`/`copy_from_user` — code that runs in kernel space rather than as a
user-space process or thread, the one mechanism CSE4600-HW1 never touched.
**Why it's worth it:** "Linux kernel basics" is explicitly named in Direction & Intent but has zero
shipped inventory anywhere in the profile; a small, working, documented driver is a concrete,
portfolio-ready first crossing of that specific line, and — once written up — a sellable reference
kit for other students on the same coursework-to-firmware track.
**First step today:** Set up a VM or container with kernel headers installed, and get the canonical
"hello world" loadable kernel module (`insmod`/`rmmod` with a `printk` in init/exit) building and
loading successfully — the baseline every later step depends on.
