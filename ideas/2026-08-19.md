## Step 2–3 — Ideas

### 1. Near-Singularity Guard Library — [Leverage]
- competence: unlabeled
- labeled_at: —

**Idea:** Extract circuit-simulator's Ruiz-equilibration-based ill-conditioning check into a
small, solver-agnostic Python package — feed it any dense linear system (not just an MNA
G/B/C/D-stamped circuit matrix) and it returns a reasoned near-singularity verdict instead of a
raw condition number or a naive determinant threshold — sold as a drop-in dependency to other
people writing their own numerical solvers.
**Leverages:** Circuit analysis `[strong]`, specifically the equilibrated condition-number
estimate that already passed a real test (a 1Ω resistor beside a 1PΩ one isn't mistaken for
genuine precision loss).
**One new thing to learn:** Generalizing the equilibration-and-estimate routine off circuit-
simulator's specific four-block matrix shape into a plain dense/sparse-matrix interface any
solver author can call without knowing MNA at all.
**Why it's worth it:** The hard part — proving the technique catches real ill-conditioning while
not false-alarming on legitimate scale differences — is already built and tested; repackaging it
generically is bounded, mechanical work with a clear buyer (anyone hand-rolling a linear solver
who currently uses a bare threshold or nothing).
**First step today:** Pull `solver.py`'s equilibration + condition-estimate routine out of the
circuit-specific code path and call it against a hand-built non-circuit matrix (e.g. a small
least-squares system) to confirm the interface holds with the circuit assumptions stripped out.

### 2. Stripe App Manifest Auditor — [Experience]
- competence: unlabeled
- labeled_at: —

**Idea:** A small CLI that reads a Stripe App's `manifest.json`, cross-checks each declared
permission against Stripe's real, current permission list, and flags any declared scope the code
never actually calls (or any scope claimed as granted that Stripe doesn't recognize) — the exact
class of bug stripe-reconciler had this week with `bank_account_read`.
**Leverages:** Applied web application security `[strong]`, specifically the manifest-vs-reality
correction made this week, not the credential-usage chokepoint already proposed 2026-08-17.
**One new thing to learn:** Programmatically fetching and parsing Stripe's actual permission-grant
reference (rather than reading it by eye, as was done this week) so the check runs unattended
instead of depending on a human re-reading docs each time.
**Why it's worth it:** This bug was real, silent, and specifically the kind static review misses —
it would have surfaced in production as every client looking like they'd revoked access. Building
the checker hardens exactly the audit habit the profile's epistemic through-line already rewards,
on a concrete, scoped artifact rather than as an abstract practice.
**First step today:** Write a first hardcoded pass that reads stripe-reconciler's own
`manifest.json`, lists every declared permission, and manually confirms which ones the codebase
actually calls — the gap between those two lists is the tool's entire reason to exist.

- competence: unlabeled
- labeled_at: —

**Idea:** A short, sold-once written guide plus a small worked-example repo teaching the specific
technique behind circuit-simulator's strongest tests — composing an assertion around a domain
invariant (conservation, convergence, a known closed-form result) instead of a bare unit check —
using the op-amp gain-convergence test, the gyrator, and the cross-source-type power-conservation

**Leverages:** Testing discipline `[strong]`, specifically this month's physically-meaningful test

2026-08-07 Threshold-Test Scaffolder idea already covered.
**One new thing to learn:** Turning a currently tacit sense of "which invariant is worth testing"
into an explicit, transferable checklist (conservation laws, known closed-form limits, symmetry)
that a reader can apply to a domain that isn't circuits.
**Why it's worth it:** It's a content asset, not freelancing — written once, sold repeatedly — and
the source material (three concrete, already-tested examples with visible before/after value) is
already sitting in a shipped repo rather than needing to be invented for the guide.
**First step today:** Write up the gyrator test as the guide's first worked example: what a bare
unit assertion would have checked, what the invariant-based version checks instead, and why the
difference would have caught a bug the bare version couldn't.
