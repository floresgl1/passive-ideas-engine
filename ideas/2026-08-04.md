  numeric divergence open on purpose until it's validated, rather than silently trusting a port

## Step 2–3 — Ideas

### 1. Port-Parity Test Harness — [Leverage]
**Idea:** Package golf's "two implementations, one held-open divergence, validated against a
threshold" pattern as a standalone dev tool: point it at two implementations of the same
numeric/ML pipeline (e.g. a Python reference and a ported Dart/Swift/Rust version), feed both
the same fixture inputs, and get a report of where outputs diverge beyond a configurable
tolerance — sold once per repo/team on a template/tool marketplace.
**Leverages:** Testing discipline plus the specific, rare pattern of deliberately running two
language implementations side by side and treating divergence as a measured quantity rather
than a bug to hide — already proven end-to-end in golf, not abstracted from anywhere else in
the profile.
**One new thing to learn:** Generalizing the fixture/comparison harness so it's pipeline-agnostic
(pluggable input generators and a configurable tolerance/metric) instead of hardcoded to golf's
specific angle and tempo outputs.
**Why it's worth it:** This is the one capability in the profile that's genuinely novel — most
teams doing a cross-language port have no systematic way to know how much their port diverges
from the source of truth. The hard part (the comparison methodology) is already validated.
**First step today:** Extract the comparison logic golf uses to hold its Python/Dart divergence
open, and rewrite its input/output interface so it takes two arbitrary CLI commands plus a
fixture directory instead of golf-specific paths.

### 2. SaaS Tenant-Security Test Pack — [Passive]
**Idea:** Extract stripe-reconciler's security test suite — CSRF origin checks with webhook
exemption, timing-attack equalization, digest-only single-use reset tokens, tenant-isolation
tests, webhook signature verification — into a drop-in pytest/Flask template that other indie
SaaS builders install and point at their own routes, sold once per project on a template
marketplace.
**Leverages:** Applied web application security [emerging] plus testing discipline [strong] —
both already shipped and CI-gated in one repo; this reframes the *test suite itself* as the
product rather than the app it protects.
**One new thing to learn:** Parameterizing the tests so they discover routes/models via
convention or a small config file instead of stripe-reconciler's hardcoded schema — the
security reasoning itself doesn't change, only its portability.
**Why it's worth it:** A template sold repeatedly with no per-sale labor is the cleanest fit for
"genuinely passive," and unlike a feature template, a security test pack keeps earning trust
(and re-sales) precisely because he already reasoned through the hard edge cases once.
**First step today:** List every security-relevant test in stripe-reconciler's backend suites
and mark which assertions are already generic (e.g. "cookie has Secure flag") versus which
assume stripe-reconciler's specific models, to scope the extraction.

### 3. Silent-Failure Severity Auditor — [Experience]
**Idea:** Build a small static-analysis CLI that scans a repo's scheduled scripts/agents (cron
jobs, GitHub Actions, LLM agent loops) for the absence of the patterns finance_bot proved matter
— staleness checks, halt-flag circuit breakers, retry budgets, enumerated error handling — and
emits a severity-classified report, sold as a one-time tool license to teams running unattended
automation.
**Leverages:** Production observability and failure handling [strong] — pre-flight validation,
staleness detection, halt flags, severity-classified silent-failure audits — previously only
ever applied *inside* finance_bot to itself.
**One new thing to learn:** Turning a manual self-audit process into an automated static
scanner (pattern-matching for the presence/absence of these guards across arbitrary codebases)
— a new tool-building skill, not a new domain.
**Why it's worth it:** This is the [Experience] pick because building the scanner forces
finance_bot's audit checklist to become an explicit, reusable rule set instead of tacit
judgment — which hardens the skill for every future unattended system he builds, this repo's
own daily/weekly routines included.
**First step today:** Write down the exact checklist finance_bot's own silent-failure audit used
(the specific patterns and their severities) as a standalone rules document, independent of
finance_bot's codebase — the seed for the scanner's rule set.

### 4. Real-Time Scheduling Visualizer — [Stretch]
**Idea:** Build a small web widget that simulates and visualizes EDF, Rate-Monotonic, and
cyclic-executive scheduling of a task set (Gantt-style timeline, missed-deadline highlighting),
targeting the same embedded-systems learner audience as the keystone circuit simulator, licensed
to bootcamps/educators alongside it.
**Leverages:** Proven web-delivery and service-architecture discipline (React/Vite, deployment,
clean separation of concerns) applied to a second hardware-adjacent domain, plus the
"schedulability analysis" reasoning already worked through in coursework.
**One new thing to learn:** Implementing schedulability-analysis math (utilization bound tests,
hyperperiod computation) as running code — one algorithm family, not a curriculum.
**Why the stretch is worth it, and why it does *not* replace the keystone:** `profile.md`
names the visual circuit simulator specifically as the shovel-ready keystone move, and that
recommendation still stands unshipped after three digests — this idea is not a substitute for
it. It's flagged here because it reuses the same delivery pattern on a second [conceptual]
hardware area (real-time scheduling) at much lower scope than the simulator's MNA solver, so if
the circuit simulator continues to stall, this is a smaller first rep at graduating the hardware
axis from zero shipped inventory.
**First step today:** Pick one scheduling algorithm (Rate-Monotonic is the simplest to verify by
hand) and implement its schedulability test against two textbook task sets with known
pass/fail answers, before touching any visualization code.
