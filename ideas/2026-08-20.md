## Step 3 — Ideas

### 1. Netlist-to-Web Circuit Visualizer — [Stretch]
- competence: unlabeled
- labeled_at: —

**Idea:** Compile the existing MNA solver to run client-side (Pyodide) and render an interactive SVG circuit diagram from a SPICE-style netlist, sold as a one-time-purchase web tool for EE students checking homework.
**Leverages:** circuit-simulator's solver, netlist grammar, and CLI — all shipped and tested (68 passing tests).
**One new thing to learn:** browser-side interactive diagram rendering (SVG/canvas circuit drawing) driven by a Pyodide-hosted Python solver.
**Why it's worth it:** the solver and netlist reader are done; only the front end is missing, and it's sold once per student repeatedly with no server cost (static site).
**First step today:** spike a single Pyodide-in-browser call to the existing `solver.py` against one saved netlist fixture, confirm it runs without a backend.

### 2. AI Ops Sub-Agent Template Pack — [Leverage]
- competence: unlabeled
- labeled_at: —

**Idea:** Package the read-only diagnostic sub-agent pattern (scoped tools, "report only" hard rule, health-snapshot script) proven independently in finance_bot and golf into a documented, config-driven template repo sold on Gumroad to solo devs running their own scheduled production systems.

### 3. SaaS OAuth Starter Kit — [Passive]
- competence: unlabeled
- labeled_at: —

**Idea:** Generalize stripe-reconciler's OAuth account-confirmation flow — AES-256-GCM refresh-token encryption with associated-data row binding, the epoch-seam provisioning pattern, the CI-caught concurrency race and its fix — into a provider-agnostic Flask boilerplate sold repeatedly as a starter kit.
**Leverages:** the OAuth flow shipped and verified end-to-end against live Stripe this week, including the fixed Connect-vs-Marketplace credential-scope bug.
**One new thing to learn:** decoupling the flow from Stripe's specific grant shape into a config-driven interface any OAuth provider can plug into.
**Why it's worth it:** this is exactly the kind of unglamorous, easy-to-get-wrong code (token storage, race conditions) that other solo SaaS builders will pay to not re-derive themselves.
**First step today:** list every Stripe-specific reference in the OAuth module (`stripe_auth()`, manifest permission checks) that would need to become a pluggable interface.

### 4. Ledger-Tieout Hosted Reconciliation API — [Passive]
- competence: unlabeled
- labeled_at: —

**Idea:** Wrap the already-published `ledger-tieout` PyPI package in a small hosted API (upload a payout/transaction list, get back a balanced journal plus a named Suspense/review report) billed via Stripe metered usage.
**Leverages:** `ledger-core`'s dispatch logic (`entries_for`, Suspense routing, the Stripe double-booking guard) and stripe-reconciler's existing Stripe integration experience.
**One new thing to learn:** Stripe's usage-based/metered billing API, distinct from the one-time/subscription billing already used in stripe-reconciler.
**Why it's worth it:** the reconciliation logic is already published and tested (680 tests, fail-closed CI) — the only new work is a thin API wrapper and billing, not new domain logic.
**First step today:** read Stripe's metered billing docs and sketch the usage-record call against one already-passing `ledger-tieout` test case.
