## Step 2–3 — Ideas

### 1. Migration Review Bot — [Leverage]
- competence: unlabeled
- labeled_at: —

**Idea:** Package stripe-reconciler's specific migration discipline — every nullable column
justified, every unique constraint written idempotently, every schema change carrying an inline
rationale note — as a GitHub Action that reviews incoming migration-file diffs on a PR and
comments per violation with the "why" attached, sold as a low-cost per-repo subscription to small
teams who don't have a DBA doing this by hand.
**Leverages:** The already-shipped, already-reasoned migration habits from stripe-reconciler —
not the double-entry math (mined twice already) and not the epoch-seam concurrency fix (mined
yesterday), but the plain schema-hygiene layer underneath both.
**One new thing to learn:** Writing each habit as a static diff-time check (parse a migration
file's DDL for a bare `ADD COLUMN ... NOT NULL` with no default, a `CREATE UNIQUE INDEX` missing
`IF NOT EXISTS`/equivalent, a schema change with no adjacent comment) instead of the runtime
tests stripe-reconciler already has.
**Why it's worth it:** This is the first time the migration-hygiene habit itself — as opposed to
what it protects — is the direct product; it's a narrower, faster build than a full security
scanner because it only has to parse DDL, not application code.
**First step today:** Write the single check for "no inline rationale comment on a schema-altering
migration" against stripe-reconciler's own migration history, and confirm it flags a deliberately
uncommented migration in a throwaway branch.

### 3. Signal-Veto Decision Gate — [Experience]
- competence: unlabeled
- labeled_at: —

**Idea:** Extract finance_bot's specific architectural rule — a noisier secondary signal
(sentiment) is wired so it can only suppress a primary decision already in flight, never
originate one on its own — into a small, domain-agnostic gating library, then prove it on one
concrete non-finance case (e.g. an LLM-based support-ticket auto-closer that a sentiment/urgency
signal can only *block* from closing, never trigger).
**Leverages:** LLM agent engineering `[strong]`, specifically the veto-vs-feature reasoning
behind finance_bot's dormant sentiment signal — an architecture decision, not a model, applied
outside finance for the first time.
**One new thing to learn:** Generalizing "primary decision + suppressive-only secondary signal"
into an interface with two named hooks (`propose()`, `veto()`) that a stranger's own primary
decision function and their own secondary signal can each plug into independently.
**Why it's worth it:** This is a rarer, harder-won asset than "we added a sentiment feature" — it
encodes a specific discipline about what a fallible extra signal is and isn't allowed to do, and
proving it holds outside finance is what turns a one-off design choice into a reusable pattern.
**First step today:** Pull the exact conditional in finance_bot that gates a BUY/SELL decision on
sentiment, rewrite its two branches as the two named hooks with finance-specific naming stripped
out, and call both hooks from one fake, unrelated decision function to confirm the interface
holds.
