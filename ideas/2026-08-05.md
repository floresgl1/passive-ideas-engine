## Step 2–3 — Ideas

### 1. Model Explainability Report Generator — [Leverage]
- competence: unlabeled
- labeled_at: —

**Idea:** Extract finance_bot's SHAP computation and model-comparison logic into a model-agnostic
CLI/library that takes any trained scikit-learn/XGBoost model plus a dataset and outputs a
polished, client-ready HTML/PDF explainability report, sold as a one-time-purchase tool to small
ML teams and consultants who need compliance-friendly explainability without building it.
**Leverages:** SHAP-based model interpretability and comparison already shipped and proven in
finance_bot's compare_models.py.
**One new thing to learn:** Templating a polished, non-technical-audience report from SHAP
output — today it lives only as internal debug plots, never a client-facing deliverable.
**Why it's worth it:** The statistically hard part (computing and comparing SHAP values
correctly) is already proven in a live system; what's left is presentation and packaging, which
is fast and sells repeatedly with no hourly billing involved.
**First step today:** Pull the SHAP computation and comparison functions out of
finance_bot/compare_models.py into a function that takes any (model, X) pair, and confirm it runs
cleanly against a toy scikit-learn model that has never seen finance_bot's data.

### 2. Document Semantic-Search API — [Passive]
- competence: unlabeled
- labeled_at: —

**Idea:** Generalize visual-search-engine's embedding/vector-DB/FastAPI stack from images to text
documents — ingest a folder of PDFs or docs, chunk and embed them, and expose a hosted semantic-
search API sold as a small monthly subscription to solo consultants and small teams who want
search over their own document set without building RAG infrastructure themselves.
**Leverages:** The already-shipped, containerized retrieval stack — embedding generation, vector
storage, similarity retrieval, REST API — proven end to end in visual-search-engine.
**One new thing to learn:** Text-specific retrieval quality tuning — chunk size, overlap, and
optional reranking — since the existing stack has only ever been exercised on image embeddings.
**Why it's worth it:** The distribution and infrastructure problem (embed, store, retrieve, serve)
is already solved; only the input modality changes, and a hosted subscription API needs no
ongoing per-customer labor once the ingestion pipeline is built.
**First step today:** Swap visual-search-engine's CLIP image encoder for a text embedding call on
a handful of sample PDFs, and confirm the existing ChromaDB + FastAPI layers accept the new vector
shape without modification.

### 3. Mobile On-Device CV Starter Kit — [Experience]
- competence: unlabeled
- labeled_at: —

**Idea:** Generalize golf's Flutter/Dart port — camera capture, on-device inference, local
persistence, share-sheet-only export — into a reusable starter template for a second, different
on-device CV use case, proving the pattern holds outside the app it was built for.
**Leverages:** The already-shipped Flutter/Dart mobile pipeline (ML Kit, ffmpeg, camera,
share_plus) from golf's port, which has so far only ever been exercised for one app.
**One new thing to learn:** Refactoring a single-call-site mobile pipeline into a package that a
second, unrelated app can consume — the discipline of proving reuse rather than asserting it.
**Why it's worth it:** Doing this once turns a one-off mobile port into a repeatable capability;
the resulting starter kit is a natural licensable/template asset afterward, but the exercise
itself is what hardens the "port and generalize" muscle for future mobile builds.
**First step today:** Identify the smallest second use case (e.g. a single-object counter or
barcode reader) that could reuse golf's camera-capture-to-on-device-inference chain, and list
exactly which files would need to change versus stay untouched.

### 4. Network Path Health Monitor — [Stretch]
- competence: unlabeled
- labeled_at: —

**Idea:** Build a small hosted monitoring tool that periodically traces and pings a customer's
key network paths (ISP uplink, VPN endpoint, self-hosted server) and alerts on latency/loss
anomalies, sold as a low-cost subscription to freelancers and small self-hosters — applying the
already-shipped observability/alerting discipline to a new, not-yet-shipped domain.
**Leverages:** finance_bot's staleness-detection and transition-only alerting pattern, and the
scheduled-automation/Discord-alerting infrastructure already proven there.
**One new thing to learn:** Turning conceptual networking knowledge (forwarding vs. routing,
transport reliability, hands-on Wireshark capture from CSE 4100) into a working measurement loop —
parsing real traceroute/ping output and defining a genuine anomaly threshold, not a course
exercise.
**Why it's worth it:** This is explicitly a stated next step in Direction & Intent ("network
diagnostics exploration"), and it reaches a not-yet-shipped domain by reusing the observability
architecture that already works, rather than re-deriving monitoring discipline from scratch.
**First step today:** Run traceroute/ping against 2–3 real destinations on the current network,
save the raw output, and sketch what a "normal" vs. "anomalous" reading would look like before
writing any collection code.
